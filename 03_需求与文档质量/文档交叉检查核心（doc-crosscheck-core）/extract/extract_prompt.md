## 输出:严格按此 schema
```json
{
  "doc": "<文档名>",
  "entities": [
    {"kind":"<类型>", "group":"<所属界面/控件块>", "fn":"<功能键,可选>", "scenario":"<场景键,可选>", "term":"<界面叫法,可选>",
     "attrs":{"text":"<文案原文>", "tokens":["<表现token>"], "when":"<触发条件>", "unclear":"<含糊处,可选>", "...":"..."},
     "evidence":"<截图相对路径,可选>"}
  ],
  "_proposals": [
    {"type":"scenario|fn|token", "key":"<你新建的key>", "cn":"<中文说明>", "reason":"<为什么菜单里没有合适的>"}
  ]
}
```

kind 取值:button / shop_entry / state / toast / reward_area / mechanism / reddot / new_mark / hotkey / anim / gamepad / field / item_frame / tab
(new_mark = New 解锁提醒,点击消失,非红点树)

## 抽取硬要求
- **多端交互稿逐条抽,禁止"与PC一致"一句带过**:功能常有【PC+手机】【手柄端】等**多份**交互稿(材料里的多个 PDF/strips)。**每一端的交互都要逐条抽成实体**——尤其手柄端的**状态机、每个按键映射(X/Y/B/RS/菜单键)、焦点转移、PC↔手柄切换、按键提示栏**,一条一条抽,`group` 标"手柄端"。**只有真的完全无差异才允许合并**;绝不能把一整端压成一个"手柄端与PC一致"的概括实体(这会让手柄端在开发中才被发现,返工)。
- **每个实体标 `group`**:它属于哪个界面/控件块(如 罗盘选择弹窗 / 分解流程 / 委托页·商城入口 / 手柄端),供工单按界面分组。
- **含糊就标 `unclear`**:读文档时,凡是该写却没写清的(数据来源没说从哪取、复用/用什么控件没指明、判定边界没写、机制不明…),在该实体 attrs 里加 `"unclear":"<哪里不清楚>"`。不要替策划脑补补全,标出来让后续报告汇总成"需求待确认"。
- `text`(Toast/按钮/状态文案)抄文档**原文,一字不差**(文本层优先,图里小字仅参考)。
- 同一语义的东西,系统文档和交互文档**要打成同一个 scenario**(这是后续比对能对上的关键)。
- 截图能佐证的实体,填 `evidence` 相对路径。
- 只抽"是什么/有什么",不要写"系统有交互没有"这类判断。
